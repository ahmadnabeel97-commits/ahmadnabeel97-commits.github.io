3. Technical map (verified in the code)
State and storage
One object S, saved to localStorage by save(), which also queues the Firebase push (schedPush). Arrays: subjects, units, topics, tasks, logs, exams, plans, gantt.
• S.plans is used by the Calendar for planned time blocks. Do not reuse that name.
• Exams: {id, name, date 'YYYY-MM-DD', subj (subjectId or '' = General)[, subjs: [subjectIds], updatedAt]}. See the exam coverage section. Deleting an exam is a hard delete (filtered out of the array, no tombstone).
• Other localStorage keys start with bcs- (banner, slot, snapshots, tracker-recovery, bcs-gt-ui = Planner view state, device-only). Backup version is BK_VER=4.
• Any NEW top-level array must be wired into: load() (normalize + default object), migrate(), the idInUse groups array near lkReconcile, buildDocs() meta, mergeIn() and applyRemote() meta branches (mergeRecordsById), and backup (bkExport, bkParse, bkApply). S.gantt is wired into all of these.
• Sync: subjects, tasks, exams, units, topics and gantt travel in the single meta Firestore doc and merge per record by id and updatedAt (mergeRecordsById, with deleted/deletedAt tombstones). Logs and plans sync per month docs. An OLD copy of the app on another device would drop gantt from meta on its next push, so use only the newest file on every device.
• Adding an optional field to an existing record type (like subjs on exams) needs no wiring: whole records are synced and backed up, and bkParse keeps unknown fields.
Syllabus tracks
SYL_TRACKS = prelim, written, bank. trkTopic(t,u) gives a topic's tracks. The primary track uses the old fields (manuallyCompleted, studyStatus); other tracks use the topic's trkDone map. Ticking goes through trkMark().
• trkProgL(st,t,u,tr) = the legacy flag-based progress. trkProg() routes Written and Bank to wsProg() and everything else to trkProgL.
• trkViewProg() single-track filter uses trkProg; the All filter averages trkProgL (flag-based).
• tkTopicRec(id) returns {t,u,sb} for a live, non-archived topic with a live unit and subject.
Written/Bank step cards
In the Syllabus, when the Written or Bank filter is active, non-archived topics render as swipe row cards (classes .rv-sw ws-sw, reusing the Mastery .rv- swipe engine and rvOpen/rvToggle/rvUndoShow).
• Swipe right = four steps: Understanding (u), Outlined (o), Writing practice (p), Writing mastery (m). Tap to check; 5-second Undo. Swipe left = Tasks (view/hide), + Task, three-dot menu.
• Optional topic field wsteps { written{u,o,p,m}, bank{u,o,p,m} } (1 = checked). With no wsteps for a track, a topic already ticked on that track counts as all four steps (legacy, stays 100%).
• Progress (wsProg): with no tasks, steps give 0/25/50/75/100; with tasks it is 50% steps + 50% tasks. 100% needs all four steps AND all tasks completed.
• wsSet() keeps the old flag in sync (flag = all four steps checked). trkMark() sets or clears all four steps for Written and Bank.
• Prelim cards (Nov 14): when the Prelim filter is active, non-archived topics ALSO render as .rv-sw ws-sw swipe cards (same engine and CSS as Written/Bank). Swipe right = ONE button, Done (button.ws-b.pd-b, data-pd=topicId; green with a check when progress >= 100). Swipe left = Tasks (view/hide), + Task, three-dot menu, same as Written. Subtitle shows "Done"/"Not done" plus "n/m tasks"; the % is the unchanged Prelim figure (trkViewProg, i.e. tasks plus manual tick). The hint line reads "Swipe right for done · left for tasks".
• pdToggle(id) does the tick: on = !(trkViewProg >= 100); trkMark(t,u,'prelim',on,now); save(); renderSyl(); wsOpen=id and wsReopen() so the swipe panel stays open; 5-second Undo via rvUndoShow, which restores manuallyCompleted, studyStatus, trkDone, wsteps and rev (so Mastery enrolment is undone). It mirrors hmTick. Click handler: the #syl click listener checks [data-wk] (Written/Bank steps), then [data-pd] (Prelim Done), then .rv-fg row toggle. The code in panel() uses a flag pdM = (sylTrack==='prelim').
• The All view still uses checkboxes (a topic there can belong to several exams). Written/Bank steps never enroll a topic in Mastery.
• Owner chose Done-only for Prelim; Prelim steps (like Written's four) were offered and declined. Do not add steps unless asked: it would change Prelim % and touch Home, Analytics and Mastery.
• Helpers: WS_STEPS, wsTrack, wsLegacy, wsGet, wsProg, wsSet, wsToggle, wsReopen. CSS prefix .ws-.
Planner (Gantt)
Location: Tasks tab → third button Planner (#tk-seg, data-tk=gantt), pane #tk-gantt / #gt. tkSub() handles it. All Planner JS sits in one block starting with the comment Planner (Gantt), step 2. CSS prefix .gt-. The page widens to 1500px on desktop while the Planner is open.
• Data: S.gantt entries {id, kind 'unit'|'topic', refId, start, end (inclusive), updatedAt[, deleted, deletedAt]}. One record per unit/topic; removing dates tombstones the record and re-adding reuses it. Bars of archived/deleted topics are hidden but their data is kept.
• Rows: subject rows (collapsible) → unit rows (arrow .gt-uc expands topics) → topic rows. Progress fill comes from trkProg for the selected track (default Prelim). A unit with topic bars but no bar of its own shows a faint dashed derived span (.gt-der). Exam markers come from S.exams (-60 to +400 days). Today line.
• View state: gtOpen (open subjects), gtOpenU (open units, which show their topics), saved with track and zoom in bcs-gt-ui.
• Expand all / Collapse all (changed this session): Expand all opens ALL SUBJECTS only; units and topics are opened manually by the owner, and units already open stay open. The button shows "Collapse all" once every subject is open (anyClosed checks subjects only). Collapse all clears both gtOpen and gtOpenU. The "N behind" chip and Auto-plan still open the specific units that hold late or newly planned topics (deliberate).
• Helpers: gtModel(), gtBarAny/gtBar/gtOk, gtKids, gtRec, gtSplit, gtDn/gtYmd (UTC day numbers, avoid DST bugs), gtDW (px per day), gtBarHtml, renderGantt, gtUiSave, gtPin, gtLate, gtPlanHtml/gtPlanRead/gtPlanCalc. Row height RH = 38px and header height HH = 66px are shared by the label column and the timeline; keep them in sync.
• Writing data: gtCommitMany([{k,id,start,end}], msg) writes several records with ONE Undo; gtCommit is the single-record wrapper (start===null removes the bar).
• Duplicate records: if two devices create a bar for the same unit/topic, two live records can exist. gtBarAny and the gtModel idx map both use the FIRST live record. Do not change one without the other.
• Interactions (desktop only; phone <700px is view-only): drag to move or stretch bars; moving a unit bar carries its topic bars (one Undo); click a bar or label opens the date sheet; drag-from-name placement (5-day unit / 3-day topic defaults); Day/Week/Month zoom; sticky month label; pinned header; behind-schedule highlighting and "N behind" chip; Auto-plan (subject, optional unit, start, deadline, weighting by open tasks, skip days; preview then Apply as ONE Undo). Details are in the code comments.

4. Mastery — current behaviour
• Optional rev object per topic {step, next, last, n, hist}. REV_STEPS = [1,3,7,14,30,60,120] days; REV_CAP = 4 per day.
• Ratings: Forgot (step 0), Hard (repeat step), Good (+1), Easy (+2).
• Only topics ticked on the PRELIM track join Mastery (revAuto at the end of trkMark). Never enrolled = rev undefined; removed = rev null and not auto re-added. Written-only and Bank-only topics are excluded everywhere (the owner was asked whether Bank topics should join Mastery and has not said; they stay out).
• UI: slim row cards; Today's revision rows swipe right = Forgot/Hard/Good/Easy, swipe left = Custom; Coming up rows show the date, swipe left for +2/+3/+4 days; tap a row also opens the options; 5-second Undo; desktop (1100px+) uses two columns.
Exam-date compression
revExam(sb) picks the exam a topic follows; revIv(step, sb) factor f = min(1, daysLeft/60); interval = max(1, round(REV_STEPS[step] * f)), then capped at max(1, daysLeft - 1) so nothing is scheduled after the day before the exam. Used by revRate (and its Undo text) and by the labels on the rating buttons in revRow. NOT applied to Custom dates, the +2/+3/+4 moves, or the first revision on enrol (1 day). revExamNote(all) shows a small line on Mastery ("Exam in N days (name) · revision intervals are shortened") when any Mastery topic's exam is under 60 days away. rev.step is unchanged, so normal intervals resume once the exam passes. Existing scheduled dates are not rewritten; they adjust the next time the topic is rated.
Exam coverage (built this session)
The owner has a multi-subject BCS exam and separate bank exams, so an exam can cover several subjects.
• Optional exam field subjs: [subjectIds] (with updatedAt when set or edited). examScope(e) = the exam's subj plus subjs, de-duplicated.
• revExam(sb) rule: the nearest upcoming exam whose scope includes the topic's subject; otherwise the nearest upcoming UNSCOPED (General) exam; otherwise none (normal intervals). Behaviour change: an exam tied to specific subjects no longer shortens other subjects' revision (previously any nearest exam was the fallback).
• UI (Exams view): the Add form has a "Covers these subjects" chip checklist (#e-cov, built in fillSelects, ticks preserved across re-renders); each upcoming exam has a Subjects button (data-ex-cov, state exCovOpen) opening an inline checklist (data-ex-chk, saved immediately; the exam's own Subject-select entry is ticked and locked). The exam list shows covered subject names.
• Tested with sample data: Bangla/English follow BCS, Banking follows the Bank exam, an uncovered subject follows a General exam; backup round trip keeps subjs.
• Not yet changed: the Analytics exam readiness card (renderExamReadinessCard) still reads only e.subj, so a multi-subject exam shows as "Overall syllabus" there.

6. Known quirks and decisions to remember
• Written/Bank topics that used to reach 100% purely through completed tasks now show at most 50% until the four steps are checked (owner's intent).
• On a Written-only topic, the old flag equals all four steps checked, so Home and other flag-based screens can show 100% while the Syllabus shows less if tasks are still open.
• Backup counts / restore preview do not list Planner bars (data is still saved and restored).
• Planner exam markers beyond about 400 days are not shown; the phone breakpoint is 700px; after a drag, label clicks are ignored for 350ms (automated tests must wait); touch drags are intentionally ignored; bars of units/topics on a different track are not shown.
• Not tested live: Firebase sync of Planner bars, or of edited exam coverage, between two real devices (only the merge function, in isolation).
• Exams created before this session have no updatedAt; edited coverage gets one, so the edited copy wins a merge. Deleting an exam is a hard delete, so an old device could bring a deleted exam back on merge.
• Compression near an exam: many topics can fall due close together; REV_CAP = 4 a day still limits what is shown, so a backlog can build.
• Prelim cards: the Done button follows the checkbox rule (progress >= 100 counts as done). A topic at 100% only through completed tasks shows green Done; tapping it clears the manual tick, which may leave it at 100% via tasks. Same as the old checkbox. Not tested on a very long real subject.
• Mastery quirks from earlier remain: Written-enrolled topics that are also on Prelim stay; bulk Start revising re-offers removed topics; leftover lv values are harmless.
